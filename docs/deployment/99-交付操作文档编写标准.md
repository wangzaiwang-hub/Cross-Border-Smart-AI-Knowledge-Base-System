# 跨境智汇 AI 知识库系统交付操作文档编写标准

## 一、文档采用手工部署方式

客户交付文档必须让没有部署经验的人按照页面和命令逐步操作，不能用下面这些方式代替教程：

1. 不使用 `.env` 文件批量注入配置。
2. 不让客户复制现成的 Compose、配置目录或部署目录后直接启动。
3. 不使用安装脚本、批处理脚本或一键启动脚本代替安装步骤。
4. 不把多个组件打包成一次批量导入或批量启动。
5. Java 后端服务由 Windows 本机 IntelliJ IDEA 手动配置并启动，不使用批量启动脚本。

MySQL、Redis、Nacos、PGVector、RocketMQ、Seata 和 Elasticsearch 等组件需要分别写清下载、安装、目录创建、配置修改、启动和验证过程。使用 Docker 的组件也要逐个执行 `docker pull`、创建目录、编辑配置和 `docker run`，不能只给一条导入整套环境的命令。

## 二、项目文件只用于核对参数

编写前必须检查项目中的 Compose、应用配置、版本锁定文件和环境台账，但这些文件用于确认项目实际参数，不代表客户教程必须直接复用 Compose 或 `.env`。

至少核对：

1. 组件最终运行在 Windows 本机、Windows Docker Desktop、WSL2、Rocky Linux 虚拟机宿主系统，还是虚拟机 Docker 容器。
2. 项目固定版本、镜像、端口、数据目录、配置文件、资源限制和安全参数。
3. 哪些 Java 服务连接该组件，应用实际读取哪些环境变量。
4. 组件之间的依赖和先后顺序，例如 Nacos 使用 MySQL 时必须先完成 MySQL。
5. 项目参数如何转换成客户需要手工填写的配置项和启动命令。

## 三、先确定客户真正需要下载和上传的对象

手工部署不等于所有组件都从源码编译。必须根据项目最终运行形态确定操作对象：

1. 最终运行在 Docker 中的组件，主流程下载和上传对象是 Docker 镜像；手动执行 Docker 安装、镜像源配置、`docker pull`、`docker save`、WinSCP 上传、`docker load`、配置目录创建和 `docker run`。
2. 最终直接运行在操作系统中的组件，才在主流程中下载软件安装包、RPM、ZIP 或源码包。
3. Java 服务最终由 IDEA 运行，交付对象是项目源码压缩包、JDK、IDEA 配置和环境变量，不把源码复制到 Redis、MySQL 等中间件容器。
4. 已有旧数据需要迁移时，源码包、旧配置和数据文件只放在迁移附录，不得放在全新部署主流程前面。

例如本项目 Redis 最终运行在 Rocky Linux 虚拟机内部的 Docker 容器中，因此主流程必须先写 Docker Engine，再写 `redis:8.4.4` 镜像，不能先要求客户源码编译 Redis。

## 四、参考原文的写作方式，不照搬错误的部署对象

用户提供的参考文档用于学习逐步操作的写法：下载地址、点击按钮、输入命令、保存目录、修改配置、输出结果、注意事项和故障排查都要保留这种详细程度。

参考文档中的版本、IP、部署对象和运行架构不能直接照搬。若参考文档写源码安装，而项目实际使用 Docker 镜像，必须把主流程改为镜像操作；有价值的源码迁移内容可以放到旧环境迁移附录。

## 五、直接从第一步开始操作

客户文档不在开头堆放“目标、背景、最终架构、阅读说明”等学术或概述内容。标题之后直接进入第一步操作。安装位置和运行位置写到对应步骤中，不集中放到开头让客户来回查找。

## 六、每一步必须写清楚

每一步至少写明：

1. **在哪里操作**：Windows 浏览器、Windows PowerShell、IDEA、WinSCP、虚拟机 SSH 终端或 Docker 容器内部。
2. **点击或输入什么**：下载网站、按钮名称、安装选项、完整命令和配置内容。
3. **安装或保存到哪里**：软件目录、安装包目录、配置文件、数据目录和日志目录。
4. **执行后的结果**：正常输出、文件、端口、进程或容器状态。
5. **哪些内容需要修改**：客户 IP、网卡、用户名、密码、盘符和目录如何替换。
6. **下一步做什么**：本步骤验证通过后，明确进入哪个步骤。

## 七、配置文件必须逐项修改

不能只说“修改配置文件”。必须写清：

- 输入什么命令打开文件。
- 搜索哪个原配置项。
- 修改前是什么。
- 修改后是什么。
- 文件保存和退出方法。
- 修改后如何验证已经生效。

密码使用明确占位符，指导客户现场生成和填写，但不能把真实密码写入文档、代码、截图或聊天记录。

## 八、启动和验证必须分开写

每个组件都要分别给出：

1. 首次启动命令。
2. 停止命令。
3. 再次启动命令。
4. 开机自启或 Docker 重启策略。
5. 端口检查。
6. 进程或容器状态检查。
7. 认证检查。
8. Windows 到虚拟机的连通性检查。
9. IDEA 中对应服务的环境变量和启动位置。

## 九、完成前必须验证

至少确认：

1. 文档没有 `.env`、Compose 批量部署、安装脚本或批量启动脚本作为客户主流程。
2. 版本、端口、镜像、变量名和资源限制与项目当前配置一致。
3. 原始参考文档的重要步骤和目录仍然保留。
4. 命令顺序可以从空环境逐步执行到组件启动成功。
5. Markdown 代码围栏完整。
6. 文档不包含真实密码、Token、API Key 或客户敏感信息。
7. 停止、删除和清理命令不会误删客户数据。
8. Docker 组件的主流程下载对象是镜像，系统组件的主流程下载对象才是安装包或源码包。

# 跨境智汇 AI 知识库系统整体开发顺序

## 一、项目开发主线

整个项目按下面的主线推进：

```text
需求与架构
→ 环境与中间件
→ Maven 工程和依赖治理
→ Common 公共能力
→ System/User/Auth/Gateway 平台主链
→ Product/Inventory 商城基础
→ Wallet/Order 交易闭环
→ Search/Knowledge 知识检索
→ AI 客服
→ Training 培训
→ Notification/Admin 后台运营
→ 治理、可观测性和部署
→ 前端共享层、商城端、管理端
→ 全量 E2E、验收和发布
```

前一阶段没有形成稳定契约和验证证据时，后一阶段可以准备原型、规格和测试数据，但不应正式接入或宣称完成。

## 二、整体开发阶段

### 第一阶段：需求、范围和架构设计

**主要内容**：

- 明确知识库、AI 客服、商城、培训和运营后台的业务范围。
- 明确不接真实支付、不接真实物流等非范围。
- 确定微服务边界、数据库所有权、同步调用和领域事件。
- 固化接口规范、权限模型、错误码、日志和测试标准。

**阶段产出**：需求规格、项目设计架构、后端交付规格、接口清单和验收标准。

**进入下一阶段的条件**：模块职责和数据所有权已经明确，不再通过开发过程临时拆服务。

### 第二阶段：开发环境和中间件基线

**主要内容**：

- Windows、Oracle JDK 25、Maven Wrapper、Node.js、pnpm 和 IDEA。
- Rocky Linux 虚拟机与 Docker Engine。
- MySQL、Redis、Nacos、PGVector、RocketMQ、Seata 和 Elasticsearch。
- 固定版本、端口、网络、资源上限、密码和备份位置。

**阶段产出**：可重复使用的开发环境、环境配置台账和中间件健康证据。

**进入下一阶段的条件**：项目依赖的基础组件能够单独启动、认证和连接，不在编码过程中临时更换组件版本。

### 第三阶段：Maven 根工程和版本治理

**开发顺序**：

```text
根 pom.xml
→ Maven Wrapper
→ ygh-dependencies
→ Maven Enforcer
→ 兼容性测试工程
```

**主要内容**：建立 Reactor 聚合、企业 BOM、JDK/Maven 版本门禁、依赖漏洞和许可证检查。

**阶段产出**：所有后续模块共同使用的构建和依赖基线。

**进入下一阶段的条件**：Oracle JDK 25 下根工程可构建，Spring Boot、Spring Cloud、Nacos、Sentinel、RocketMQ 和 Seata 代表类兼容。

### 第四阶段：Common 公共能力

**开发顺序**：

```text
ygh-common-core
→ ygh-common-test
→ ygh-common-web
→ ygh-common-security
→ ygh-common-mybatis
→ ygh-common-redis
→ ygh-common-mq
```

**主要内容**：统一响应、错误码、分页、领域事件、异常处理、安全上下文、数据库审计、Redis 规范、MQ 幂等和测试基座。

**阶段产出**：业务服务可以直接复用的公共代码，不再各自复制基础实现。

**进入下一阶段的条件**：公共模块测试通过，并且不反向依赖任何业务模块。

### 第五阶段：平台主链

**开发顺序**：

```text
ygh-system-api / ygh-system-service
→ ygh-user-api / ygh-user-service
→ ygh-notification-api / ygh-notification-service 基础能力
→ ygh-auth-service
→ ygh-gateway
```

**为什么这样排**：System 提供角色、权限和配置事实；User 提供用户、员工和组织事实；Auth 需要调用 System 和 Notification；Gateway 最后消费稳定的认证、用户和服务发现契约。

**阶段产出**：注册、登录、刷新、退出、用户资料、组织权限、基础通知和统一网关链路。

**进入下一阶段的条件**：Gateway → Auth → User/System 的真实登录链路通过，Nacos 注册、JWT、权限、内部签名和 Redis 会话稳定。

### 第六阶段：商城基础

**开发顺序**：

```text
ygh-product-api
→ ygh-product-service
→ ygh-inventory-api
→ ygh-inventory-service
```

**主要内容**：类目、品牌、SPU/SKU、价格、批次、溯源、商品缓存、库存状态机和库存流水。

**阶段产出**：商品可以浏览和运营，库存可以查询、锁定、确认和释放。

**进入下一阶段的条件**：商品缓存一致性、库存并发、超卖防护和重复请求幂等测试通过。

### 第七阶段：交易闭环

**开发顺序**：

```text
ygh-wallet-api
→ ygh-wallet-service
→ ygh-order-api
→ ygh-order-service
→ RocketMQ 交易事件和对账
```

**为什么这样排**：Order 创建和支付流程依赖 Product、Inventory、Wallet 和 User，必须等这些契约稳定后开发。

**阶段产出**：购物车、订单快照、库存锁定、虚拟充值、模拟支付、退款、履约、Outbox 和三方对账。

**进入下一阶段的条件**：注册 → 充值 → 下单 → 支付 → 模拟履约完整链路通过，重复请求或消息不会重复扣款、扣库存。

### 第八阶段：搜索基础和知识库

**开发顺序**：

```text
ygh-search-api
→ ygh-search-service 的 Elasticsearch/PGVector 基础
→ ygh-knowledge-api
→ ygh-knowledge-service
→ 搜索增量索引、全量重建和别名切换
```

**为什么这样排**：Knowledge 发布后的解析、切片和索引需要 Search 提供稳定入口；Search 的商品索引又依赖 Product 契约。

**阶段产出**：文档上传、审核、版本、解析切片、关键词检索、向量检索、融合排序和权限过滤。

**进入下一阶段的条件**：只有已审核、有效且有权访问的知识能够进入搜索结果，文档版本和来源可追溯。

### 第九阶段：AI 客服与 RAG

**开发顺序**：

```text
ygh-ai-api
→ 模型适配层
→ RAG 检索与引用
→ 商品/库存/订单受控工具
→ SSE 流式回答
→ AI 治理、评测和安全
```

**主要依赖**：System、Search、Knowledge、Product、Inventory 和 Order。

**阶段产出**：基于有效知识和实时业务工具的多轮问答、引用、拒答、反馈、评测和模型治理。

**进入下一阶段的条件**：回答引用可核验，无证据时拒答，模型不能越权读取或修改核心业务数据。

### 第十阶段：培训系统

**开发顺序**：

```text
ygh-training-api
→ 课程和学习路径
→ 任务分配
→ 服务端学习进度
→ 测验、评分和解锁
→ 培训统计
```

**主要依赖**：User、Knowledge 和 Notification。

**阶段产出**：岗位课程、章节阅读、学习任务、闯关测验、成绩、解锁和后台统计。

**进入下一阶段的条件**：岗位课程 → 阅读 → 测验 → 解锁链路通过，进度由服务端计算，员工只能访问本人课程。

### 第十一阶段：通知完善和运营后台

**开发顺序**：

```text
Notification 接入订单、知识审核和培训事件
→ ygh-admin-api
→ ygh-admin-service
```

**主要内容**：补齐业务通知、重试、死信和人工补偿；建设运营总览、AI 治理、索引任务、消息积压、服务状态和审计聚合。

**阶段产出**：完整的异步通知链路和运营后台聚合接口。

**进入下一阶段的条件**：Notification 重复消费幂等；Admin 只调用公开只读 API，不跨库读取、不成为新的业务事实源。

### 第十二阶段：服务治理、可观测性和运维代码

**主要内容**：

- Nacos 配置、OpenFeign 超时、Sentinel 限流熔断和 Seata 边界。
- Actuator、Prometheus 指标、结构化日志、traceId 和告警。
- Secret 扫描、SBOM、依赖漏洞、日志脱敏和安全测试。
- 备份、恢复、索引重建、消息重放和资源治理。

**阶段产出**：服务可以监控、降级、审计、备份和恢复。

**进入下一阶段的条件**：故障可识别、问题可定位、数据可恢复，资源受限环境不会无界增长。

### 第十三阶段：自动化测试和部署交付

**开发顺序**：

```text
API/依赖兼容测试
→ 契约测试
→ 集成测试
→ 安全测试
→ 性能测试
→ 服务 Dockerfile
→ 场景部署与恢复验证
```

**阶段产出**：后端发布候选版本、OpenAPI、请求集、Mock、镜像、部署配置、健康检查、回滚和恢复证据。

**进入下一阶段的条件**：后端业务闭环可以脱离前端独立验收，P0/P1 缺陷清零。

### 第十四阶段：前端共享层和商城端

**开发顺序**：

```text
ygh-web-shared
→ 登录与会话
→ 商城首页/商品/购物车/订单/钱包
→ 知识库与 AI
→ 培训与个人中心
```

**为什么后开发**：前端需要消费稳定的 OpenAPI、权限、错误码、Token 刷新、上传下载和 SSE 协议。视觉原型可以提前，真实接口接入应在后端契约稳定后进行。

**阶段产出**：`ygh-web-mall` 的完整真实接口页面。

**进入下一阶段的条件**：类型检查、生产构建、401/403、Token 刷新和主要用户流程通过。

### 第十五阶段：运营管理前端

**开发顺序**：

```text
管理端登录与权限路由
→ 组织和 RBAC
→ 商品、订单和通知运营
→ 知识和培训管理
→ AI 治理、审计和系统状态
```

**阶段产出**：`ygh-web-admin` 的完整运营管理界面。

**进入下一阶段的条件**：菜单、按钮和接口权限一致，管理操作具备确认、错误反馈和审计语义。

### 第十六阶段：全项目 E2E、验收和发布

**最终验证顺序**：

```text
全量 Maven Reactor
→ 前端 type-check/build
→ 登录 E2E
→ 商城 E2E
→ 知识与 AI E2E
→ 培训 E2E
→ 管理后台 E2E
→ 安全与性能复验
→ 部署和恢复演练
→ Secret/许可证/SBOM 检查
→ Pull Request、main、Tag 和 Release
```

**最终产出**：可追溯的源码版本、测试报告、部署包、操作文档、数据库迁移、镜像摘要和发布说明。

**项目完成条件**：全部业务场景、前后端、部署、备份恢复和安全门禁通过，不以“代码已经写完”代替项目验收。

## 三、允许并行但不能打乱依赖的工作

1. UI 视觉原型可以在后端开发期间并行，但真实接口接入必须等待 OpenAPI 稳定。
2. Notification 可以先完成基础站内信能力，订单、知识和培训事件在对应业务模块完成后逐个接入。
3. 测试工程从公共模块阶段就开始建设，但全量 E2E 必须等待完整业务链路。
4. Dockerfile、监控和安全扫描可以随模块同步补充，最终部署验收仍放在业务代码完成后。
5. 文档必须跟随每个阶段同步更新，不能全部留到发布前补写。

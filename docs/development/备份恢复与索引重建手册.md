# 备份恢复与索引重建手册

## 备份范围

- MySQL 全库包含 Nacos 配置库和所有业务事实库，使用一致性快照、存储过程和事件导出。
- PGVector 使用 PostgreSQL custom format 导出。
- 知识库及培训附件使用压缩归档，并与数据库备份放在同一时间戳目录。
- Elasticsearch 不作为事实来源，不做主备份；从已发布知识和商品事件重建。
- 每次备份生成 `SHA256SUMS`，恢复前强制校验。

## 恢复流程

1. 停止写入流量、Outbox 调度和索引任务。
2. 执行 `restore-data.sh BACKUP_DIR --confirm`，恢复 MySQL、PGVector 和附件。
3. 旧附件目录自动改名为 `.before-restore-时间戳`，确认无误后再人工清理。
4. 启动 Search，通过内部索引生命周期接口创建新的 `knowledge-vN` 索引版本。
5. 管理员调用 `POST /api/v1/admin/knowledge/index-jobs/rebuild`，请求体为 `{"version":"knowledge-vN"}`。系统仅从 MySQL 中未过期的已发布知识生成幂等 UPSERT 任务；重复调用不会重复入队。
6. 等待索引任务全部成功，确认 PGVector 与 Elasticsearch 文档数一致。
7. 调用索引切换接口将 `knowledge-active` 原子切换到新版本。
8. 执行登录、商城、知识检索、AI 引用和培训学习冒烟检查，再恢复流量。

开发环境目标为 RPO 24 小时、RTO 4 小时；企业环境目标为 RPO 1 小时、RTO 2 小时。实际达标结论必须以集中测试阶段的恢复演练计时证据为准。
